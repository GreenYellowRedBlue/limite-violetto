# Candidate Windows and Linux shader toolchains

## Scope and identities

This report addresses [Assess the candidate Windows and Linux shader toolchains](https://github.com/GreenYellowRedBlue/limite-violetto/issues/4) for the pinned llama.cpp/ggml candidate `296538adea19ff397100bf8e7d71f302d2d2bb35`, against the immutable accepted brief at [`173c50ea1f11b4b68ad8eb350b40c8b464ae64d5`](https://github.com/GreenYellowRedBlue/limite-violetto/blob/173c50ea1f11b4b68ad8eb350b40c8b464ae64d5/docs/specs/limite-vulkan-spec.md). The candidate targets are Windows 11 x64/MSVC v143 and Ubuntu 24.04 x64/GCC 13, with CMake 3.31.x and Vulkan SDK 1.4.328.1. These are source/toolchain candidates, not measured build or device support.

## Findings

| Area | Primary-source evidence | Meaning and limit |
|---|---|---|
| SDK headers | LunarG's [Vulkan SDK 1.4.328.1 release notes](https://vulkan.lunarg.com/doc/view/1.4.328.1/windows/release_notes.html) identify Vulkan-Headers tag `vulkan-sdk-1.4.328.0`. The full core header at that tag lacks declarations for `VkPhysicalDeviceCooperativeMatrixDecodeVectorFeaturesNV`, `VkPhysicalDeviceShaderMixedFloatDotProductFeaturesVALVE`, and `VkPhysicalDeviceShaderOCPMicroscalingTypesFeaturesEXT`. | This absence alone is **not** a compile blocker. Pinned [`ggml-vulkan-types.h`](https://github.com/ggml-org/llama.cpp/blob/296538adea19ff397100bf8e7d71f302d2d2bb35/ggml/src/ggml-vulkan/ggml-vulkan-types.h) has guarded local fallback typedefs for all three: NV lines 28–37; VALVE lines 135–148; EXT lines 150–163. Whether the full source compiles with the SDK remains untested. |
| Vulkan CMake prerequisites | Pinned [`ggml/src/ggml-vulkan/CMakeLists.txt`](https://github.com/ggml-org/llama.cpp/blob/296538adea19ff397100bf8e7d71f302d2d2bb35/ggml/src/ggml-vulkan/CMakeLists.txt) has minimum CMake 3.19; discovers Vulkan and requires `glslc` plus SPIRV-Headers via CONFIG. Its shader-generator subdirectory [`vulkan-shaders/CMakeLists.txt`](https://github.com/ggml-org/llama.cpp/blob/296538adea19ff397100bf8e7d71f302d2d2bb35/ggml/src/ggml-vulkan/vulkan-shaders/CMakeLists.txt) builds a C++17 generator. | CMake 3.31.x is above the declared minimum, but this is not a successful configuration/build observation. Recipe must provide compiler, Vulkan SDK/glslc, and discoverable SPIRV-Headers package. |
| Shader feature test | The same Vulkan CMake's `test_shader_extension_support` invokes `glslc --target-env=vulkan1.3`, then bases its test on a particular stderr substring. | It does not test the process result/status as a compile-success criterion; substring absence is not reliable evidence of a valid successful shader compile. Independently check exit status, nonempty output, and SPIR-V validity. |
| SPIR-V / capabilities | The [SDK SPIR-V toolchain documentation](https://vulkan.lunarg.com/doc/view/1.4.328.1/windows/spirv_toolchain.html) identifies compiler/optimizer/validator tools; the pinned Vulkan CMake explicitly targets `vulkan1.3`. [Khronos Vulkan SPIR-V environment rules](https://docs.vulkan.org/spec/latest/appendices/spirvenv.html) define legal module capabilities. | Tool availability and a target flag do not establish emitted-module validity, enabled float controls/subgroups or device support. Validate each actual module with pinned `spirv-val` and dispatch its required target path. |
| C++ / compiler-sensitive arithmetic | The shader generator explicitly requests C++17. CMake/toolchain declarations do not prove host compiler behavior for contraction or optimizer transformations. | Keep contraction/optimization qualification empirical and source-specific: compare diagnostic output and generated SPIR-V/dispatch results against accepted semantics; do not infer from compiler brand/version. |
| Portable arithmetic paths | The brief and accepted ADRs specify canonical BF16 conversion (NaN result `0x7FC0`), required FP32 arithmetic boundaries and representation/serialization distinctions. The pinned Vulkan backend contains BF16-related matrix/row/copy and scalar-FP32 attention routes, alongside F16 paths/fusions; its generic binary shader variants are F32/F16, RMSNorm is F32→F32 and unary pipelines match F32 or F16. | Storage support or a backend supports-op predicate does not establish the required operation/shape/dtype pipeline or complete BF16 semantics. Treat portable FP32 with explicit narrowing as conditional pending exact diagnostic compilation and execution. Existing pinned `fp32_to_bf16` helper uses add-round-shift without a NaN branch; it does not establish the canonical NaN rule for all inputs. |
| Feature/device dispatch | Vulkan backend source checks support and constructs pipelines, while the brief requires particular extensions, float controls and subgroup behavior. | Source evidence is not GPU feature evidence. Query physical-device properties/features and dispatch the actual required diagnostic kernels on the target; neither Windows nor Linux target dispatch was measured here. |

## Isolated diagnostic recipe prerequisites (not executed)

Use the already pinned source revision and immutable, locally provisioned tool inputs; keep all outputs/build trees isolated from the normal root CUDA/HIP and serving environment. Configure a diagnostic Vulkan-only build with CUDA and HIP disabled, explicit MSVC v143 or GCC 13, CMake 3.31.x, SDK 1.4.328.1, `glslc`, SPIRV-Headers CONFIG package, and SPIR-V tools. Record exact compiler, SDK/header, CMake and tool versions and configure flags. This is a recipe outline, not a selection or approval of a new SDK/build.

End-user SDK independence requires checking the resulting distributable/runtime behavior on clean target environments without an SDK installed: build-time shader tools and headers must not become end-user runtime prerequisites. That property is unverified.

## Unexecuted falsification checklist

1. For each OS/compiler tuple, configure the pinned tree in a fresh isolated diagnostic build directory with Vulkan on and CUDA/HIP off; capture full configure output and resolved package/tool paths.
2. Compile the native Vulkan backend and shader generator. Treat a missing-type error as unresolved until verifying the three guarded local typedefs and exact SDK headers used by that build.
3. Compile every required diagnostic shader with the selected `glslc` and explicit Vulkan target; require successful process status and nonempty module, then run the matching pinned `spirv-val` for every module. Inspect required extension/capability, float-control and subgroup declarations.
4. Exercise canonical BF16 conversion including NaNs, FP32 exceptions/narrowing boundaries, contraction-sensitive expressions, representative operation/shape/dtype pipelines and optimizer-sensitive comparisons. Compare semantics to the accepted brief; do not equate compilation with correctness.
5. On the RX 6900 XT, query and record actual Vulkan extensions/features/float controls/subgroup properties, create the real pipelines, and dispatch diagnostic cases with output checks. A CPU compile or Vulkan software device cannot qualify target dispatch.
6. Test the resulting packaged runtime in clean Windows/Linux environments without installed SDKs; confirm no SDK/tool dependency leaks into runtime requirements.

## Resolution

Primary source supports a plausible isolated recipe for both named host targets and does **not** establish an SDK incompatibility: the three missing SDK declarations are locally supplied by pinned guarded fallbacks. CMake's shader feature probe is substring-only and must not serve as the compile-success gate. The research question is answered at the source/prerequisite level; no native or shader build, SPIR-V validation, BF16 diagnostic, end-user SDK-independence check, or RX 6900 XT feature query/dispatch was run. Therefore compatible-source candidates remain unmeasured and neither toolchain nor target-device qualification is claimed. This informs [Provision isolated pinned diagnostic build toolchains](https://github.com/GreenYellowRedBlue/limite-violetto/issues/9), [Test BF16 and shader boundaries in isolated diagnostics](https://github.com/GreenYellowRedBlue/limite-violetto/issues/10), and [Select the evidence-backed engine pin and minimal patch boundary](https://github.com/GreenYellowRedBlue/limite-violetto/issues/13); it does not resolve a new SDK or build decision.
